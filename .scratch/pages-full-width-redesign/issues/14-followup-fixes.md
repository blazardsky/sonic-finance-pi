## Comments

**Reminders card** (`web/src/pages/Dashboard.tsx`, `web/src/lib/strings.ts`): `t.reminders` changed to "Promemoria pagamenti di questo mese" (confirmed via grep it's used nowhere else). The per-row `Switch` (`checked`/`onCheckedChange`) became a `Toggle` (`pressed`/`onPressedChange`) — independent per row, not `ToggleGroup`, since any number of reminders can be enabled at once. Icon swaps `RiBellFill`/`RiBellLine` on state; a new `t.reminderToggleLabel(label, enabled)` string gives it an accessible name ("Disattiva/Attiva {label}"), since the visible row label already names the reminder. `switch.tsx` is now unused app-wide but left in place, same as `native-select.tsx`'s standing exception — it's a stable shadcn primitive, not dead app code.

**Report annuale**: one class change on the root `<div>`, `max-w-2xl` → `max-w-(--content-max-width)`. Nothing else touched.

**Form sidebar containment** — the substantial one. `web/src/components/ui/sidebar.tsx`'s `Sidebar` gained a `contained` prop (desktop, offcanvas + variant="sidebar" only) and `web/src/components/form-sidebar.tsx` passes it.

First attempt used `position: sticky` for the desktop panel, scoped to `<main>` (the nearest ancestor with `overflow-auto`). Live testing (Playwright, comparing `main.scrollHeight`/`clientHeight` against `document.documentElement.scrollHeight`/`window.innerHeight`) proved `<main>` never actually overflows in this app — the shell's outer wrapper uses `min-h-svh` (a floor, not a cap), so the whole document grows and the *window* scrolls, not `<main>`. Per spec, `sticky` sticks within its nearest ancestor scroll container regardless of whether that container currently overflows — since `<main>` has `overflow-auto` but never scrolls, a sticky panel bound to it never engages and just scrolls away with the page like `position: static` would. Not an App.tsx bug worth chasing (out of scope for this ticket anyway) — ticket 02's own comments confirm the *original* (pre-containment) panel was always `fixed` to the viewport, "exactly like the main nav sidebar," and that already satisfied "stays visible while the list scrolls" trivially, by never moving at all regardless of scroll.

Landed on: keep `position: fixed` (so it's still viewport-scroll-immune, matching the original), but stop hardcoding the horizontal edge at the literal viewport boundary. The `contained` branch renders a normal in-flow "gap" placeholder (reserves the row's width, shrinks to 0 on offcanvas collapse, same as the default branch's own gap div) plus the actual `fixed` panel. A `ResizeObserver` + `resize` listener on the gap element measures `getBoundingClientRect()` and derives `right`/`left` (viewport px) from it, applied as an inline style — so the panel docks to wherever the *centered content column's* edge actually is, recalculated on any resize, instead of assuming it's flush with the window. Vertical stayed `inset-y-0 h-svh`, matching the original/default branch exactly (no change needed there — `fixed` is unconditionally immune to scroll). A `onContainedEdgeChange` callback prop reports the same measured value up so `FormSidebarTrigger` (a sibling, not a descendant) can dock itself against the identical edge rather than duplicating the measurement.

Verified via Playwright at 2200×900 on Categorie: panel/trigger rects were pixel-identical before and after `window.scrollBy(0, 1000)` — genuinely scroll-immune now, not just theoretically. Offcanvas collapse/expand re-verified with real `page.mouse.click()` (not `.click()` — see below): panel width animates to 0, trigger tracks the edge across the transition, both correctly reversible.

**Bug found and fixed during this verification, unrelated to the positioning logic above**: the desktop trigger button used `top-1/2 -translate-y-1/2` for vertical centering. Tailwind v4 compiles `-translate-y-1/2` to the standalone CSS `translate` property (not the `transform` shorthand) — `getComputedStyle` confirmed `transform: none` / `translate: 0px -50%`. Combined with `position: fixed` and an element whose other inline styles are updated by React on every measurement, this left Chromium's hit-test region ~16px stale relative to where the button actually painted: `document.elementFromPoint()` at the button's visual center correctly reported the button itself, and Playwright's `.click()` timed out claiming a sibling `<div>` "intercepts pointer events" — but the tell was that a genuine `page.mouse.click()` at that same visual center silently did nothing (no navigation, no state change), while `element.click()` (a synthetic DOM dispatch bypassing hit-testing) worked immediately. Fixed by replacing the transform-based centering with `top-[calc(50%-1rem)]` (the button is `size-8`/2rem, so half is 1rem) — no `translate` property involved. Re-verified with a real `page.mouse.click()`: the collapse/expand toggle now works from an actual OS-level click, not just a synthetic one.

Live-verified (Playwright, dev servers already running): reminders card renders the new title and a working `Toggle` (clicked it, confirmed `aria-label`/`data-state` flip and the PATCH request implied by the label change, then reverted); Spese and Categorie at 2200×900 — panel/trigger dock to the content column's edge, not the literal viewport edge (right≈2110 of 2200, matching the app shell's own padding); scroll-immunity and collapse/expand confirmed as above; mobile (390px) still opens the full-width Sheet via the FAB, confirmed via a real mouse click after fixing an unrelated test-selector ambiguity (not a product bug — Playwright's `text=Spese` matched a Dashboard card title before matching the nav link); Report annuale now measures `max-width: 1800px` (the `--content-max-width` value) instead of the old `max-w-2xl`.
