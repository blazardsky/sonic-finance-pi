## Comments

Implemented in `web/src/pages/Expenses.tsx`: root container is now `mx-auto flex w-full max-w-(--content-max-width) flex-col gap-6 p-6`; layout is a `flex flex-wrap gap-6` row with the table in a `flex-1 min-w-0` column on the left and `<FormSidebar>` (ticket 02) on the right, holding the add/edit form as its `children` with `title={editing === null ? t.addExpense : t.editExpense}`. A new `sidebarOpen` state is passed to `FormSidebar`'s `open`/`onOpenChange`, and `selectExpense` now sets it `true` alongside loading the draft, so choosing "Modifica" from a closed panel actually reopens it (desktop) instead of updating a hidden form. Row actions: the table gained an `Azioni` column with a `DropdownMenu` ("..." `RiMoreLine` trigger) offering "Modifica spesa" (`RiEditLine`) and a destructive "Elimina" (`RiDeleteBinLine`); this replaces the old whole-row click-to-edit (removed, along with its now-unneeded `scrollTo`, since the panel is `fixed` and no longer needs scrolling into view) and adds a new capability — Delete no longer requires entering edit mode first. `remove()` became `removeExpense(e: Expense)`, callable directly from any row. Category, Payer, Payment-method and each Item row's Category now use the new `Select`/`SelectTrigger`/`SelectValue`/`SelectContent`/`SelectItem` in place of `NativeSelect` (Payment-method's optional "none" state uses a `NO_PAYMENT_METHOD` sentinel, since Radix `Select.Item` rejects an empty string value). The date field uses ticket 01's `DatePicker` (which gained an `id` prop in this ticket, for `FieldLabel htmlFor` linking). Amount uses `Field`/`FieldLabel` + `InputGroup`/`InputGroupAddon`/`InputGroupInput` for the € adornment; Date/Category/Tax-year/Store/Payer/Payment-method/Note all moved to `Field`/`FieldLabel` (+`FieldDescription` for the tax-year hint), replacing the hand-rolled `<label>` wrapper. The details disclosure is now a shadcn `Accordion` (single, collapsible) instead of native `<details>`, driven by a `detailsOpen` state that mirrors the original's `open={editing !== null}` transition (opens on `selectExpense`, closes when an edit finishes or is cancelled/deleted) while still letting the household toggle it manually in between. Item rows, Store's datalist-suggest `Input`, and the overall submit/cancel/delete button arrangement are otherwise unchanged in behaviour.

Bug found and fixed via live testing (not caught by `tsc`/build): Payer lives inside the details `Accordion`, and Radix unmounts closed `AccordionContent`, so the browser's native `required` check on the hidden Payer `Select` never ran — a brand-new draft (Payer never touched) could reach the server and 400 with "an expense needs a payer", surfacing only as the generic "Spesa non salvata. Riprova." Added an explicit check in `submit()` (new string `t.invalidPayer`, "Scegli chi ha pagato.") that opens the disclosure and shows the real reason. This wasn't specific to Expenses' particular fields — it's a consequence of moving any required-but-collapsed field from native `<details>` (which, confirmed by a small isolated test, does *not* exempt its content from constraint validation while closed) to Radix `Accordion` (which does) — worth remembering for the other six form+list tickets if any of them put a required field inside their own details disclosure.

Two more bugs surfaced by live-testing this ticket's actual page, both in ticket 02's `web/src/components/form-sidebar.tsx` / `web/src/components/ui/sidebar.tsx` rather than anything specific to Expenses, fixed here since this was the first real exercise of that component:
- The desktop trigger button was rendered in normal document flow, positioned to end up right after the sidebar's flow-reserved gap — but the actual panel is `position: fixed` to the *viewport*, which sits on top of (and, at this page's width, exactly over) that in-flow position, making the trigger invisible/unclickable whenever the panel was open (the default state). Fixed by making the trigger itself `fixed` too, anchored to the real edge (`right-0` closed, `right-(--sidebar-width)` open) with a `z-20` above the panel's `z-10`.
- The panel's colours used the `Sidebar` primitive's hardcoded `bg-sidebar`/`text-sidebar-foreground` (the main nav's own blue branding) unconditionally regardless of `variant`, contradicting the spec's "shares --background/--border" intent for this panel. A CSS-custom-property override attempt worked on desktop but not on mobile (the mobile Sheet renders through a Radix Portal, so it isn't a DOM descendant of the ancestor doing the overriding, and custom-property inheritance follows the DOM tree, not the React tree) — so `Sidebar` instead gained a `themed?: boolean` prop (default `true`, preserving the main nav's look) that swaps those two classes for `bg-background`/`text-foreground` at all three places they're hardcoded (desktop outer wrapper, desktop inner panel, mobile `SheetContent`); `FormSidebar` passes `themed={false}`.
- Separately (not a bug, a genuinely missing capability): the mobile Sheet was always an 18rem partial drawer — fine for the main nav, but the spec calls for a *full-width* drawer for a form takeover. `Sidebar` gained a `mobileWidth?: string` prop (default the existing 18rem constant, so the main nav is unaffected) forwarded to the Sheet's width variable; getting it to actually win required matching `SheetContent`'s own `data-[side=*]:w-3/4` selector shape (a plain `w-(--sidebar-width)` override loses to that on specificity) and neutralising its `sm:max-w-sm` cap the same way. `FormSidebar` passes `mobileWidth="100vw"`.

Verified live: reset the local dev DB's password (`db/sonic.db`, gitignored, with the user's explicit go-ahead) to log into `go run ./cmd` + `pnpm --dir web dev` via a scripted headless-Chromium session (Playwright, since `chromium-cli` wasn't installed). Confirmed at 1280px, 1920px and 390px: full-width layout at laptop/wide, the form sidebar open/closed/reopen-on-edit, the mobile FAB opening a genuinely full-width drawer, the row dropdown's Modifica (loads the row, reopens a closed panel) and Elimina (confirm dialog, DELETE, row count drops) both working end to end, a real add-expense submission (Select category, open details, Select payer, submit) landing in the list, and the panel/labels rendering in normal page colours on both desktop and mobile. `npm run build` (`tsc -b && vite build`) passes clean throughout.
