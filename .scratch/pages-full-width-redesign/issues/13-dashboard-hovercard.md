## Comments

Implemented in `web/src/pages/Dashboard.tsx`, scoped exactly as instructed: only the `import` block (added `HoverCard`/`HoverCardContent`/`HoverCardTrigger`) and the `ClientsCard`/`ClientAlert` functions changed — `git diff --stat` shows 64 insertions / 4 deletions, all inside that one file, nothing touching the container width or the rest of the page's layout.

`ClientAlert` (shared by both lists) became generic over its item shape (`T extends { key, name, date? }`) and gained a required `hoverContent: (client: T) => ReactNode` render-prop, so each caller supplies exactly what it has without `ClientAlert` needing to know which list it's rendering. "In attesa di pagamento" (`waiting`) now carries `amountCents`/`daysWaiting` through from `OutstandingIncome` (both already in the same `/api/pending-payments` payload this card was already fetching — no new request), and its `hoverContent` shows `€ {formatCents(amountCents)}` and `t.waitingDays(daysWaiting)` (the same phrase Month.tsx's own pending-payments list already uses). `total_earned_cents` was left out per the ticket's own instruction: it lives on `/api/clients`, a request `ClientsCard` has never made, and Dashboard's `load()` doesn't fetch it for anything else either — adding it here would be exactly the "a new request just for a hover detail" the ticket says to avoid.

"Forse da fatturare" (`unbilled`) has nothing numeric to surface at all — `NotYetInvoicedClient` is just `{client_id, client}`, no amount, no days, and (same reasoning as above) no `total_earned_cents` without a new request. Its `hoverContent` instead shows `t.notYetInvoicedHint` — the existing "billed in recent months, not yet this one" explanation, which is otherwise only ever shown once, list-level, on Month.tsx's `PendingPayments`; Dashboard's condensed badge-only version of the same list had no explanation at all before this, so surfacing that hint per-entry is a genuine addition within the "whatever of the above is available" instruction, not padding.

Bug found and fixed via live testing (not a `tsc`/build-time issue): a bare `<HoverCard>` never opens on touch at all — Radix's own source (`@radix-ui/react-hover-card`) explicitly wraps its pointer handlers in `excludeTouch`, which no-ops any event with `pointerType === "touch"`, by design (there is no such thing as a "hover" on a touchscreen). Since this ticket's own manual-verification line names tapping explicitly, that's not a corner case to leave broken. Fixed by extracting the badge+HoverCard pairing into a small `ClientBadge` component with its own controlled `open` state (`useState` + `onOpenChange`) and a plain `onClick` that toggles it — Radix's controlled-component plumbing (`useControllableState`) means the existing hover-driven open/close keeps working exactly as before (it still calls the same `setOpen`), while the added `onClick` covers the touch case a real household's phone actually needs. Confirmed via a headless-Chromium touch-context session (`hasTouch: true, isMobile: true`) that a `.tap()` on a client badge now opens the card with the correct content, and a separate desktop-context `.hover()` still does too.

One harmless side effect noted, not fixed: wrapping `Badge` in `HoverCardTrigger asChild` means Radix's `Slot` merge gives the trigger's own `data-slot="hover-card-trigger"` precedence over `Badge`'s own `data-slot="badge"` on the rendered element — confirmed via `grep` that nothing in this codebase's CSS or JS selects on `data-slot="badge"`, so this has no visible or functional effect; left alone rather than adding an extra wrapper element to avoid it.

Verified live: reused the dev password from tickets 03–12, `go run ./cmd` + `pnpm --dir web dev`, scripted headless-Chromium (Playwright). Confirmed: hovering a "Giovanni" badge in "In attesa di pagamento" shows a card reading "€ 1.234,00 / in attesa da 5 giorni" (matching the real `/api/pending-payments` data), a touch-context tap opens the same card, and the Dashboard's other cards/layout are visually unchanged around it. The "Non ancora fatturato" list's own `hoverContent` wasn't exercised against live data in this session (this dev db's `not_yet_invoiced` came back empty) — it shares the identical, already-verified `ClientBadge`/`HoverCard` mechanism, just with static hint text instead of computed figures. `npm run build` (`tsc -b && vite build`) passes clean throughout.
